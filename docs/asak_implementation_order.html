ASAK-back · 2인 팀 기준

백엔드 구현 순서

프론트 담당 그대로 이어서: Kiosk 트랙 / Admin 트랙 병렬 진행. 각 트랙 안에서는 선생님 방향대로 수직 슬라이스로 짭니다.

트랙 분리: Kiosk(com.asak.user)와 Admin(com.asak.admin)은 패키지가 갈려있어 파일 충돌이 거의 없음 — 동시 진행 가능. 공유 파일은 ErrorCode.java 하나뿐.

순서 (선생님 지정): 메뉴 조회 → 주문·결제 흐름. 완료 기준: 메뉴 선택부터 주문 완료까지 실제 DB 기반으로 한 번 끝까지 동작.

수직 슬라이스로 짠다: 한 기능을 Controller → Service → Mapper → XML → DB까지 전부 뚫어서 확인하고 다음 기능으로 — 레이어별로 전부 다 만들어놓고 나중에 연결하지 않음. Admin 쪽도 쓰기 작업 5개를 하나씩 이 방식으로.

이 문서 읽는 순서
  1. 기능 우선순위에서 이번에 만들 기능을 고른다.
  2. 공통 절차를 따라 Controller부터 DB 확인까지 한 기능을 끝낸다.
  3. 주문 목록 예시를 보고 목록 조회 API의 최소 형태를 잡는다.
  4. 마지막으로 Kiosk / Admin 트랙에서 담당별 세부 파일과 순서를 확인한다.

만들 기능 우선순위 — 다음에 무엇을 할지

이 순서로 가는 이유: Kiosk의 주문·결제는 메뉴 데이터가 있어야 하고, Admin의 운영 기능은 주문·결제 데이터가 쌓여야 의미가 있다. 따라서 “화면 개수”가 아니라 앞 기능의 결과를 다음 기능이 쓰는 순서로 만든다.

병렬 규칙: Kiosk와 Admin은 패키지가 갈려 있어 읽기 API까지는 병렬 진행 가능하다. 다만 한 사람이 같은 공통 파일(ErrorCode.java, 응답 봉투, DB View)을 동시에 수정하지 않는다.

0공통 기반 확인 — 기능을 만들기 전 1회

새 화면을 만들기 전에 서버·DB·공통 응답 구조가 실제로 동작하는지 확인한다. 여기는 “기능 구현”이 아니라 이후 모든 기능의 출발점이다.

  • 첫 확인: GET /api/health, DB 연결 로그, ApiResponse, GlobalExceptionHandler
  • 완료 기준: 서버가 뜨고 Bruno에서 health 200을 받으며, compileJava가 성공한다.
  • 다음: 메뉴 조회로 이동한다. 공통 파일을 새로 만들거나 구조를 갈아엎지 않는다.
1Kiosk 메뉴 조회 — 주문의 재료 만들기Kiosk 우선

카테고리 → 메뉴 목록 → 메뉴 상세를 실제 DB에서 읽는다. 주문 생성보다 먼저 끝내야 가격, 옵션, 품절 정보를 서버가 다시 검증할 수 있다.

  • 시작 파일: UserMenuMapper.java / UserMenuMapper.xml
  • 대상 API: /api/kiosk/categories, /api/kiosk/menuList, /api/kiosk/menuDetail/{menuId}
  • 완료 기준: 카테고리 하나와 메뉴 하나를 Bruno에서 조회하고, 메뉴의 가격·옵션·품절 값이 DB와 같다.
  • 다음: 주문 생성으로 이동한다.
2Kiosk 주문 생성 — 가장 중요한 수직 슬라이스둘이 함께

프런트가 보낸 가격을 믿지 않고, 메뉴·옵션·제외 재료·수량·품절을 DB에서 다시 확인한 뒤 주문을 저장한다.

  • 시작 파일: UserOrderMapper.java와 주문 검증용 Mapper DTO
  • 대상 API: POST /api/kiosk/orders
  • 완료 기준: 정상 요청은 orders와 order_item에 저장되고, 가격 조작·품절·수량 오류는 ErrorCode로 거절된다.
  • 다음: 결제 승인으로 이동한다. 주문 생성이 불안정하면 Admin 화면부터 만들지 않는다.
3Kiosk 결제 승인 — 주문 흐름 닫기Kiosk 우선

주문 존재·이미 결제됨·결제 금액·결제수단을 검사한 뒤 payment를 저장한다. 여기까지 끝나야 “주문 완료”가 실제 데이터가 된다.

  • 시작 파일: UserPayMapper.java / UserPayService.approvePayment
  • 대상 API: 결제수단 조회와 POST /api/kiosk/payments
  • 완료 기준: 같은 결제 요청을 두 번 보내도 중복 승인되지 않고, payment 상태와 주문 상태가 일관된다.
  • 다음: Admin 읽기 API로 이동한다.
4Admin 읽기 API — 운영자가 실제 주문을 보기Admin 병렬 가능

운영 화면에 필요한 데이터를 먼저 읽는다. 쓰기 기능보다 조회가 먼저여야 상태 변경 전후를 눈으로 확인할 수 있다.

  • 추천 순서: 주문 목록 → 주문 상세 → 활성 주문 보드 → 메뉴 상세
  • 시작 파일: AdminOrderMapper.java / AdminOrderMapper.xml
  • 완료 기준: 주문번호·총금액(totalAmount)·상태·품목 정보가 실제 DB와 같고, 빈 목록도 200 응답으로 처리한다.
  • 다음: 주문 상태 변경으로 이동한다.
5Admin 상태 변경과 운영 설정 — 읽은 뒤에 쓴다Admin

상태 변경·품절·결제수단·메뉴 수정처럼 DB를 바꾸는 기능은 하나씩 수직 슬라이스로 끝낸다.

  • 추천 순서: 주문 상태 변경 → 결제수단 설정 → 품절 관리 → 메뉴 생성/수정 → 주문 취소/환불
  • 공통 규칙: 상태 전이와 재고/품절 판단은 Service에서 검증하고, 각 UPDATE 뒤 DB 값을 확인한다.
  • 완료 기준: 성공·실패·중복 클릭·이미 변경된 상태를 Bruno로 각각 확인한다.
  • 다음: Dashboard와 Sales 집계로 이동한다.
6Dashboard·Sales·프런트 실연동 — 마지막에 묶기

집계 화면은 주문·결제·취소 데이터가 쌓인 뒤 만든다. 화면의 mock을 실 API로 바꾸는 작업도 각 API Bruno 검증 뒤에만 시작한다.

  • 추천 순서: Dashboard 요약 → 일별 매출 → 월별 매출 → 화면별 mock 교체 → 회귀 테스트
  • 완료 기준: 취소/환불이 집계에서 올바르게 반영되고, 프런트의 Loading·Empty·Error 상태도 확인한다.
  • 마지막 확인: 기능별 Bruno 요청, DB 값, 프런트 화면, 문서의 API 예시를 모두 같은 상태로 맞춘다.

선택한 기능 구현법 — 공통 절차

0코드를 열기 전에 화면·계약·DB를 먼저 확정

목표: “무엇을 조회/저장하고, 성공하면 어떤 JSON을 주는가”를 먼저 한 장으로 정리한다. 이 단계가 없으면 Mapper 컬럼명과 화면 필드명이 뒤늦게 달라진다.

  • Screen ID와 화면 상태: Default, Loading, Empty, Error, Disabled 상태와 화면 이동을 확인한다. 목록 화면이면 빈 목록도 정상 응답인지 먼저 결정한다.
  • Product Bible / API 문서: URL, HTTP 메서드, 요청값, 응답 필드를 적는다. ASAK 응답은 { success, status, code, message, data } 봉투를 사용한다.
  • DB 출처: 테이블인지 View인지, 기준 키가 무엇인지, 조인이 필요한지 확인한다. 추측한 컬럼명으로 XML부터 작성하지 않는다.
  • 재사용 파일: 같은 도메인의 Controller, Service, Mapper, DTO가 있는지 먼저 찾는다. 새 이름을 만들기보다 기존 패키지·응답 형식을 따른다.
START GATE: Screen ID · URL · 성공 JSON · 빈 데이터 처리 · DB 출처를 모두 말로 설명할 수 있을 때만 구현 시작
1응답 DTO와 필드 이름을 고정

목표: DB 컬럼을 화면에 그대로 노출하지 않고, 프런트가 사용할 camelCase DTO를 정한다.

  • 목록은 “행 하나” DTO부터 만든다. 예: orderId, orderNo, orderType, orderStatus, totalAmount, createdAt.
  • 금액은 숫자형으로 보내며, 주문 총액의 API 이름은 totalAmount를 사용한다. 화면의 문자열 “91,500원” 표시는 프런트가 담당한다.
  • 목록 DTO와 상세 DTO를 억지로 합치지 않는다. 상세에만 필요한 items, 옵션, 제외 재료는 상세 응답에 둔다.
  • DTO를 만든 뒤에는 Bruno 응답 예시를 한 번 적어 본다. 예시 JSON을 만들기 어렵다면 필드 정의가 아직 불완전한 상태다.

WHY: DTO는 DB 구조 변경이 화면까지 새는 것을 막는 경계다. SQL의 total_price는 DTO에서 totalAmount로만 바꾼다.

2Mapper 인터페이스와 XML을 한 쌍으로 작성

목표: Java 메서드 이름, XML id, SQL 결과 별칭이 정확히 한 기능을 가리키게 한다.

  • Mapper 인터페이스에 반환 타입을 먼저 정한다. 목록은 보통 List<...Response>, 단건은 DTO 한 개다.
  • XML의 namespace는 Mapper의 전체 패키지명과 같아야 하며, select id는 Java 메서드명과 같아야 한다.
  • SQL은 필요한 컬럼만 조회하고 DTO 이름으로 별칭을 준다. 예: total_price AS totalAmount, created_at AS createdAt.
  • 단순 행은 resultType, 부모·자식 목록처럼 중첩 구조가 있으면 resultMap과 각 중첩 레벨의 id를 사용한다.
  • 파라미터가 있으면 Mapper의 @Param 이름과 XML의 #{...} 이름을 반드시 맞춘다. null을 넘기면서 XML에서 그 속성을 참조하면 런타임 500이 된다.
MAPPER GATE: XML만 읽어도 “어느 DB 값이 어느 DTO 필드로 가는지” 추적 가능하고, SQL을 DB 도구에서 먼저 실행해 본다.
3Service는 기능 규칙을, Controller는 HTTP만 담당

목표: 코드가 길어지는 이유를 레이어별 책임으로 분리한다. 단순 조회라면 Service는 Mapper 호출과 최소 조립만 한다.

  • Service: 조회 조건 기본값, 상태 전이, 가격 재계산, 트랜잭션처럼 “업무 규칙”을 둔다. Controller에 SQL·DB 조건을 넣지 않는다.
  • Controller: URL과 HTTP 메서드를 받고 Service를 호출한 뒤 ApiResponse.success(...)로 감싼다. JSON API Controller에는 @RestController를 사용한다.
  • 주의: @Controller는 HTML View를 찾는 용도다. JSON API에 붙이면 반환 객체를 화면 이름으로 해석해 내부 경로가 중복되거나 정적 리소스 오류가 날 수 있다.
  • 예외: 예상 가능한 업무 실패는 CustomException(ErrorCode.XXX)로 표현한다. 모든 예외를 500으로만 보이게 하면 URL 오타와 DB 오류를 구분하기 어렵다.
4Bruno로 URL → HTTP 상태 → JSON → DB 순서 검증

목표: “빌드 성공”이 아니라 실제 요청 한 번이 끝까지 통과했는지 확인한다.

  • 환경 변수 baseUrl은 http://127.0.0.1:8080처럼 서버 주소까지만 둔다. 각 Bruno 요청 파일이 /api/... 경로를 붙인다.
  • 먼저 GET /api/health로 서버가 떠 있는지 확인하고, 다음에 대상 API를 호출한다.
  • 성공이면 HTTP 200뿐 아니라 success: true, 업무 code, data 모양, 한글 값까지 확인한다.
  • 조회 API는 실제 DB 행과 응답 한 행을 비교한다. 쓰기 API는 요청 전후 DB 값, 중복 호출, 실패 입력까지 확인한다.
  • 500이면 로그의 첫 예외를 본다. NoResourceFoundException은 URL/Controller 문제일 수 있고, SQL 예외는 Mapper·컬럼·파라미터를 먼저 본다.
VERIFY GATE: Bruno 성공 응답 캡처 + 서버 로그 이상 없음 + 실제 DB 값 일치 + compileJava 성공

예시 템플릿 — Admin 주문 목록

A첫 번째 파일: 목록 행 DTO

처음 시작할 파일은 Controller가 아니라 DTO다. “표 한 줄에 무엇이 보이는지”를 그대로 적으면 이후 Mapper와 SQL이 쉬워진다.

파일: src/main/java/com/asak/admin/dto/response/OrderListResponse.java

// 표의 한 행 = DTO 한 객체
// TODO: 화면에 정말 필요한 필드만 남긴다.
private Long orderId;
private String orderNo;
private String orderType;
private String orderStatus;
private String paymentStatus;
private int totalAmount;       // DB total_price가 아니라 API 이름
private LocalDateTime createdAt;
private int itemCount;
private String menuSummary;
여기까지의 확인: 화면 표의 각 열이 DTO 필드 하나와 연결되는지 말로 설명한다. 문자열 “91,500원”은 DTO에 넣지 않는다.
B두 번째·세 번째 파일: Mapper 메서드와 SQL 뼈대

Java가 “무엇을 받을지” 선언하고, XML이 “어떻게 조회할지” 채운다. 두 이름은 반드시 같아야 한다.

파일: AdminOrderMapper.java → src/main/resources/mappers/AdminOrderMapper.xml

// AdminOrderMapper.java
List<OrderListResponse> getOrderList(@Param("filter") OrderListFilter filter);

<!-- AdminOrderMapper.xml -->
<select id="getOrderList"
        resultType="com.asak.admin.dto.response.OrderListResponse">
  SELECT
    order_id AS orderId,
    order_no AS orderNo,
    total_price AS totalAmount,
    created_at AS createdAt
    -- TODO: 화면에 필요한 나머지 열을 DTO 이름으로 별칭 처리
  FROM vw_order_list_summary
  ORDER BY created_at DESC
  LIMIT #{filter.limit} OFFSET #{filter.offset}
</select>

팀원이 채울 곳: View/테이블 이름, 나머지 SELECT 열, 정렬 기준. 먼저 DBeaver에서 SQL을 실행해 행이 나오는지 확인한 뒤 XML에 옮긴다.

C마지막 파일: Service와 JSON Controller 연결

목록만 필요할 때는 외부 필터를 받지 않는다. Service가 Mapper가 요구하는 최소 기본값만 만들고, Controller는 JSON 봉투로 반환한다.

// AdminOrderService.java
public Map<String, Object> getOrderList() {
  // TODO: XML이 요구하는 기본값을 만든다. 예: offset=0, limit=20
  OrderListFilter filter = OrderListFilter.builder()
      .offset(0)
      .limit(20)
      .build();

  return Map.of("content", adminOrderMapper.getOrderList(filter));
}

// AdminOrderController.java
@RestController                    // JSON API에는 Controller가 아니라 RestController
@RequestMapping("api/admin/orders")
public class AdminOrderController {
  @GetMapping
  public ApiResponse<Map<String, Object>> getOrders() {
    // TODO: 성공 code/message는 프로젝트의 기존 표현을 따른다.
    return ApiResponse.success("...", "...", adminOrderService.getOrderList());
  }
}
STOP LINE: 여기서 목록 조회가 200이면 완료다. 필터·정렬 UI·페이지 이동은 다음 작업으로 넘긴다. 지금 한 파일에 같이 넣지 않는다.
DBruno 정답 확인표

코드를 다 쓴 뒤에는 아래 네 칸이 모두 맞아야 “목록 API 완료”다.

  • URL: GET {{baseUrl}}/api/admin/orders. baseUrl에는 http://127.0.0.1:8080만 둔다.
  • HTTP: 200 OK
  • 봉투: success: true, code: ADMIN_ORDER_LIST_SUCCESS, data.content: [] 또는 주문 배열
  • DB 대조: 응답 첫 행의 orderNo, totalAmount, createdAt이 DB 조회 결과와 같은지 확인

현재 확인 범위 — Admin 주문 목록을 가장 작게 끝내기

사용자 요청: GET /api/admin/orders 한 번으로 주문 목록을 조회한다. 아직 화면 필터와 페이지 버튼을 실제 API에 연결하지 않는다.

흐름: AdminOrderController.getOrders() → AdminOrderService.getOrderList() → AdminOrderMapper.getOrderList(...) → AdminOrderMapper.xml → vw_order_list_summary.

응답: data.content 배열의 각 행에 주문번호, 주문유형, 주문/결제 상태, 총 금액, 생성시각, 품목 수, 메뉴 요약을 담는다. 프런트는 이 배열을 표의 행으로 반복 렌더링한다.

지금 하지 않는 것: 검색 조건, 정렬 UI, 실제 페이지 이동, 상세 패널 연동은 목록 응답이 안정적으로 확인된 다음 별도 작업으로 분리한다. “목록 조회”에 이 기능들을 함께 넣지 않는다.

트랙 1 — Kiosk

1메뉴 조회

목표: 카테고리 → 메뉴 목록 → 메뉴 상세, 실제 DB 데이터로 응답 옴

  • UserMenuMapper.java + .xml
  • 응답 DTO 4개 (CategoryResponse, MenuListResponse, IngredientResponse, MenuDetailResponse)
  • UserMenuService — 매퍼 위임만, 로직 거의 없음
  • UserMenuController에 3개 엔드포인트

코드는 asak_kiosk_backend_reference.html "응답 DTO"/"UserMenuMapper" 섹션 그대로 가져다 씀

GATE: 메뉴 목록/상세 API가 실제 DB 값으로 응답하는 것 확인 후 다음으로
2주문 생성페어링 — 둘이 같이

목표: 가격·품절·옵션·제외재료 서버 재검증 → 주문번호 생성(충돌 재시도) → orders/order_item/order_item_option/item_exclusion 트랜잭션 저장

  • UserOrderMapper.java + .xml, mapper.dto 4개(MenuPriceCheck 등)
  • UserOrderService.createOrder — 힌트 박스 순서대로 (가격 재계산 → 주문번호 재시도 → 저장)
  • UserOrderController 엔드포인트 연결

이 프로젝트에서 로직상 제일 까다로운 부분이라 둘이 같이 짬 — 리드는 누가 해도 상관없이 같이 코드리뷰/페어프로그래밍. CustomException(ErrorCode.XXX)로 던짐 — BusinessException 아님. 코드는 asak_kiosk_backend_reference.html "UserOrderMapper"/"Service 힌트" 섹션 참고.

GATE: 주문 생성 API가 실제 DB에 orders/order_item 저장하는 것 확인 후 다음으로
3결제 승인

목표: 결제 승인 API가 검증 후 payment 저장, 실패 처리 포함

  • UserPayMapper.java + .xml

  • UserPayController 엔드포인트 연결
GATE(완료 기준): 메뉴 선택 → 옵션 선택 → 주문 생성 → 결제 승인까지 Postman/Bruno로 실제 DB 찍어가며 한 번에 끝까지 통과
4키오스크 ↔ 백엔드 연동

Phase 1~3이 실제로 통과한 다음에만 시작 — mock 데이터를 실제 API 호출로 교체

트랙 2 — Admin

Kiosk 트랙과 별개로 처음부터 병렬 진행 — 패키지가 갈려있어 파일 충돌 없음. 단, Kiosk Phase 2(주문 생성)는 페어링이라 그 시간엔 잠깐 합류.

1읽기 API 연결 확인 (이미 매퍼·DTO는 반영됨)

목표: 주문 상세·메뉴 상세가 Controller까지 뚫려서 실제 DB로 응답

  • AdminOrderMapper/AdminMenuMapper — 이미 있는 코드 그대로 (asak_admin_backend_reference.html "반영됨" 태그)
  • AdminOrderController/AdminMenuController/AdminOrderService/AdminMenuService에 getOrderDetail/getMenuDetail 엔드포인트 연결
  • getLiveOrders()는 건드리지 않음 — 별도 DTO 경고 주석 그대로 유지
GATE: 주문 상세/메뉴 상세 API가 실제 DB 값으로 응답 확인
2쓰기 작업 5개 — 하나씩 수직 슬라이스

전부 코드 없음, 힌트만 있는 상태(asak_admin_backend_reference.html "쓰기 작업 힌트"). 추천 순서: 단순한 것부터.

  • ① 결제수단 설정 — pay_method_cfg 한 줄 UPDATE, 제일 단순
  • ② 품절 토글 — 영향 메뉴 개수 쿼리는 이미 있음(view.sql [18]번)
  • ③ 주문 상태 변경 — INVALID_ORDER_STATUS_TRANSITION 이미 ErrorCode에 있음
  • ④ 메뉴 생성/수정 — 이미지 업로드 경로 설정 있음
  • ⑤ 주문 취소/환불 — 조건 분기 제일 까다로워서 마지막

하나 완성될 때마다 DBeaver로 실제 UPDATE 확인 — 5개 다 끝나면 Kiosk Phase 4(연동)와 같이 프론트 붙임

동기화 지점

공유 파일: ErrorCode.java — 누구든 먼저 건드리는 사람이 커밋하고 상대에게 pull 알림 (동시 수정 시 충돌)

완료 기준은 Kiosk 트랙 안에서 끝남: "메뉴 선택→주문 완료"는 Kiosk 트랙(메뉴조회→주문생성→결제승인) 혼자서 통과시키는 목표라, Admin 진행 상황과 무관하게 확인 가능. Admin은 자기 페이스대로 5개 쓰기 작업 진행하면 됨.
