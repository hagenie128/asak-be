읽기 vs 쓰기

  • DTO·매퍼(아래)는 실제 프로젝트 파일 그대로 — 주문 상세·메뉴 상세 조회는 이미 동작하는 상태
  • 쓰기 작업(맨 아래)은 힌트만 — 코드가 아직 하나도 없고, 뭘 조심해야 하는지만 정리

응답 DTO

com.asak.admin.dto.response — 패키지가 com.asak.user랑 구분해주니 Admin 접두어는 안 붙입니다. 옵션/제외재료/알레르기/옵션항목은 뷰가 만든 JSON을 @JsonRawValue로 그대로 통과시킵니다.

AdminOrderMapper

getLiveOrders()는 그대로 둡니다 — 주문 관리 상세용 OrderDetailResponse와 절대 같은 DTO로 합치지 않는다는 경고 주석이 이미 코드에 있습니다.

AdminOrderMapper.java반영됨
package com.asak.admin.mapper;

import java.util.Map;
import org.apache.ibatis.annotations.Param;
import com.asak.admin.dto.response.OrderDetailResponse;

public interface AdminOrderMapper {

  Map<String, Object> getLiveOrders();

  // 주문 관리 상세 화면 전용. getLiveOrders()의 DTO와는 별개로 유지한다.
  OrderDetailResponse getOrderDetail(@Param("orderId") Long orderId);
}

<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN" "https://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.asak.admin.mapper.AdminOrderMapper">

<resultMap id="orderDetailMap" type="com.asak.admin.dto.response.OrderDetailResponse">
  <id column="order_id" property="orderId"/>
  <result column="order_no" property="orderNo"/>
  <result column="order_type_code" property="orderType"/>
  <result column="status_code" property="orderStatus"/>
  <result column="total_price" property="totalAmount"/>
  <result column="created_at" property="createdAt"/>
  <collection property="items" ofType="com.asak.admin.dto.response.OrderItemResponse"
              column="order_id" select="findOrderItems"/>
</resultMap>

<select id="getOrderDetail" resultMap="orderDetailMap">
  SELECT order_id, order_no, order_type_code, status_code, total_price, created_at
  FROM vw_order_summary
  WHERE order_id = #{orderId}
</select>

<select id="findOrderItems" resultType="com.asak.admin.dto.response.OrderItemResponse">
  SELECT menu_id AS menuId, menu_name AS menuName, quantity, unit_price AS unitPrice,
         option_items AS optionItems, excluded_ingredients AS excludedIngredients
  FROM vw_order_item_full
  WHERE order_id = #{orderId}
</select>

</mapper>

  SELECT m.id AS menu_id, m.cat_id AS category_id, c.name AS category_name,

  JOIN category c ON c.id = m.cat_id

쓰기 작업 — 힌트만 (코드 없음)

Controller/Service 코드는 안 씁니다. 여기 5개는 전부 아직 매퍼도 없는 상태입니다.

주문 상태 변경 — PATCH /api/admin/orders/{orderId}/status

  • RECEIVED→PREPARING→COMPLETED 순서만 허용, 역행/건너뛰기 막아야 함
  • 전이 불가 시 INVALID_ORDER_STATUS_TRANSITION — ErrorCode에 이미 있음

주문 취소 / 환불

  • 결제 전 취소 = orders.status→CANCELED + canceled_at 세팅
  • 결제 후 환불 = payment.status→REFUNDED + refunded_at 세팅
  • 결제 승인 안 된 주문은 환불 자체가 불가 — 취소만 가능. 같은 메서드로 뭉치면 조건 분기가 헷갈리기 쉬우니 처음부터 분리

메뉴 생성 / 수정 — POST·PATCH /api/admin/menus

  • 삭제(DELETE)는 계약서에 "지원 안 함" 명시됨 (soft-delete 컬럼 없음) — 만들 필요 없음
  • 이미지 업로드 경로는 application.properties의 app.file.menu-upload-dir 이미 있음

품절 토글 — PATCH /api/admin/soldOut

  • changes[] 배열로 여러 건 한 번에 받음, targetType에 따라 menu.sold_out/ing.sold_out/opt_item.sold_out 중 어디를 UPDATE할지 분기
  • "영향 메뉴 개수" 미리보기 쿼리는 이미 있음(view.sql [18]번) — 실제 UPDATE 후 그 쿼리 재사용하면 affectedMenuCount 나옴

결제수단 설정 — PATCH /api/admin/payment-methods/{methodId}

  • pay_method_cfg 한 줄 UPDATE라 5개 중 제일 단순함
