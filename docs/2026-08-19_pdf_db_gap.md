## 1. [P1] 옵션 42쌍이 중복 등록 — 키오스크 화면 중복 노출

`opt_item` 에 같은 이름이 두 개씩 있고, **두 개가 같은 정책에 함께 연결**돼 있다.

```
#320 견과류  add=900 amt=15.00 G ing=182 created=2026-07-03
#327 견과류  add=900 amt=15.00 G ing=182 created=2026-07-03   ← 모든 속성 동일

두 id 모두 policy #15, #16, #17 에 연결됨
```

**(메뉴, 옵션명) 조합 2,925건에서 같은 옵션이 두 번 노출된다.** 고객 화면에 "견과류"가 두 줄로 보인다는 뜻이다.

중복 그룹별 분포:

| 그룹 | 총 옵션 | 중복 |
|---|---|---|
| 토핑 추가 | 57 | 다수 |
| 세트 음료 | 14 | 7쌍 전부 |
| 세트 사이드 | 10 | 5쌍 전부 |
| 베이스 변경 | 6 | 3쌍 전부 |
| 드레싱 선택 / 추가 | 15 / 15 | — |
| 재료 빼기 | 40 | — |

합계 **중복 이름 42건**.

### 함부로 지우면 안 되는 이유

양쪽 id 가 **모두 실제 주문에 쓰이고 있다.**

| 옵션 | id A (주문) | id B (주문) |
|---|---|---|
| 견과류 | #320 (1,871건) | #327 (1,869건) |
| 그라브락스연어 | #278 (1,788건) | #290 (1,776건) |
| 그린밀싹 | #351 (3,836건) | #358 (3,808건) |
| 단호박크림스프 | #341 (5,098건) | #346 (5,071건) |

거의 정확히 반반이다. 실제 운영 흔적이 아니라 **시드 생성 시 두 벌이 만들어지고 주문 시드가 무작위로 골라 쓴 결과**로 보인다. `created_at` 도 2026-07-03 으로 동일하다.

### 계획

1. **조사** — 왜 두 벌이 생겼는지 `asak-data/seed-v3/opt_item.json` 과 생성 스크립트를 확인한다. 시드 단계 결함이면 재생성 절차부터 고쳐야 재발하지 않는다.
2. **표시 문제 우선 차단** — 데이터를 건드리기 전에 화면 중복부터 막는 것이 급하다. 조회 쪽에서 옵션명 기준 중복 제거를 넣을지, 정책 연결(`opt_policy_item`)에서 한쪽만 남길지 정한다. **정책 연결만 끊으면 주문 이력은 그대로 보존된다.** 가장 안전한 1차 조치다.
3. **통합은 나중에** — `opt_item` 행 자체를 합치려면 `order_item_option.opt_item_id` 를 한쪽으로 옮겨야 한다. 주문 46만 건이 걸린 작업이라 백업·검증 계획을 따로 세운다. 통계가 토핑별로 쪼개지는 문제(LMIS-MENU-005 인기 토핑 통계)를 실제로 겪기 전까지는 미뤄도 된다.

> 결정 필요: 2번에서 **조회 쪽 중복 제거**와 **정책 연결 정리** 중 무엇을 먼저 할지.

## 2. [P2] menu_nutr 결측 — PDF 로 22개 메뉴 채울 수 있음

`menu_nutr` 73행 중 kcal 등 주요 항목이 15행 비어 있었다. 신버전 PDF 로 대부분 해결된다.

| 필드 | 채울 행 |
|---|---|
| serving_g | 23 (생수 포함) |
| kcal · carb_g · sugar_g · protein_g · fat_g · saturated_fat_g · sodium_mg | 각 14 |

대상은 그동안 비어 있던 사이드·음료가 대부분이다 — 크림스프 3종, 치킨토마토 스튜, 카사바칩, 착즙주스 3종, 코크제로, 스프라이트제로, 애사비, 리얼 수박 주스, 아메리카노 HOT/ICE. 여기에 신메뉴(고추장제육 3종, 프로틴 샌드위치 2종, 바질크림 잠봉 랩, 청양간장 두부 비빔밥, 치킨 콥 샐러디)가 더해진다.

특이 처리:

- **아메리카노 HOT/ICE** — PDF 에 온도 구분 없이 「아메리카노」 하나(290g·22.5kcal). 양쪽에 같은 값을 넣는다.
- **생수 330ml** — PDF 에 없다. 물이므로 `serving_g = 330` 만 기록하고 나머지는 비워 둔다.

### 반드시 지킬 것

**기존 값은 덮지 않는다.** PDF(8/13)와 DB 기존값이 45건 다른데, DB 는 CSV(8/12) 기준으로 들어가 있다. 어느 쪽이 정본인지 확정되지 않았으므로 `NULL` 인 칸만 채운다.

> 결정 필요: PDF 8/13 이 CSV 8/12 보다 최신이므로 **기존 값도 PDF 로 갱신할지** 별도 판단이 필요하다. 갱신한다면 45건 차이를 먼저 눈으로 확인해야 한다.

### 실행 방법

`docs/tools/fill_nutrition.py` 를 준비해 뒀다. `--apply` 없이 실행하면 미리보기만 한다.

```bash
python docs/tools/fill_nutrition.py            # 미리보기
python docs/tools/fill_nutrition.py --apply    # 백업 후 반영
```

`--apply` 는 `backup_20260819_menu_nutr_before_pdf_fill` 과
`backup_20260819_menu_ing_before_serving_g` 를 먼저 만들고, `NULL` 인 칸만 UPDATE 한다.

## 3. [P3] menu_ing.quantity 257행 — ing_nutr.serving_g 로 채울 수 있음

`menu_ing` 411행 중 330행(80%)이 `quantity` 결측이다. `ing_nutr.serving_g`(재료 표준 제공량)가 근거가 된다.

검증: `quantity` 가 이미 있는 행과 대조하면 `serving_g` 와 73% 일치한다. 불일치는 소스류 3종(바베큐소스·바질페스토·고추장비빔)뿐인데 `menu_ing` 이 50g, `ing_nutr` 이 10~30g 이다. **소스 50g 은 과하므로 `ing_nutr` 쪽이 옳다.**

`serving_g` 값이 재료 특성에 정확히 맞는 것도 근거다 — 김자반·후리가케 3g, 소스류 10g, 견과류 15g, 크림스프 200g, 착즙주스 240g. 반면 기존 `menu_ing.quantity` 는 **`50.00` 아니면 `0.00` 두 종류뿐**이라 일괄 입력된 더미값으로 보인다.

- 채울 수 있음: **257행** (`unit_id` 는 257행 모두 이미 채워져 있어 손댈 필요 없음)
- 남는 결측 73행: `ing_nutr.serving_g` 자체가 없는 재료 (채소, 곡물, 통밀 치아바타 등)

> 결정 필요: `quantity = 0.00` 인 24행. 재료가 들어가는데 0g 이라 결측을 0 으로 메운 것으로 보인다. 그중 16행은 `serving_g` 로 교정 가능하다. 실제 값인지 결측인지 확정이 필요하다.
