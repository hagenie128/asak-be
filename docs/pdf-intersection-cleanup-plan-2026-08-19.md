# PDF 교집합만 남기기 — 산출 결과와 검토

> 작성일: 2026-08-19
> 요청: 영양성분표 PDF(`nutrition_260813`)와 DB 양쪽에 있는 메뉴·옵션만 남긴다
> 상태: **산출만 했다. DB 는 변경하지 않았다.**
> **결론부터: 이 기준을 그대로 적용하는 것은 권하지 않는다. 이유는 2절.**
> 2026-08-19 운영 결정은 3-4절에 기록했다. 이 결정은 코드·DB 반영 전이며, 실행 검증은 아직 하지 않았다.

## 1. 산출 결과

PDF 를 다시 파싱했다. 200건이 나왔으나 같은 표가 두 번 실려 있어 **고유 항목은 110건**이다.
같은 이름인데 값이 다른 항목은 0건이라 파싱은 신뢰할 만하다.

| 대상 | 유지 | 삭제 |
|---|---|---|
| 메뉴 (활성) | 57 | **15** |
| 옵션 | 88 | **27** |

## 2. 이 기준을 권하지 않는 이유

**PDF 는 영양성분 공개 문서이지 판매 품목 마스터가 아니다.** 판매 중이어도 PDF 에 없을 수 있다.

### 2-1. 명백히 잘못 지워지는 것들

| 삭제 대상 | 주문 | 왜 PDF 에 없나 |
|---|---|---|
| `생수 330ml` | 0건 | **물이라 영양성분이 없다.** 판매 상품이다 |
| `시저` (드레싱) | 5,532건 | PDF 드레싱 9종에 없을 뿐 현역이다 |
| `허니머스타드` | 5,256건 | 〃 |
| `(저당) 들기름소이` | 4,545건 | 〃 |
| `고추간장 소스` | 3,985건 | 〃 |
| `김자반` (토핑) | 3,509건 | 소량 토핑이라 표에 없다 |
| `베이컨` | 3,613건 | PDF 에는 `칩베이컨` 만 있다 (다른 품목) |
| `스크램블에그` | 3,536건 | PDF 에 없다 |

이 9개만 합쳐도 주문 3만 건 이상이다. 원문을 직접 확인했고 파서 문제가 아니라 **PDF 에 실제로
없는 것**이 맞다. 그러나 없다는 사실이 곧 단종을 뜻하지는 않는다.

### 2-2. 「재료 빼기」 15개는 개념상 PDF 에 있을 수 없다

`김자반 빼기`, `화이트치즈 빼기` 같은 항목은 **주문 시 재료를 제외하는 동작**이다. 영양성분표에
실릴 성질이 아니다. 이 기준으로 지우면 **재료 제외 기능(FWD-MENU-007)이 부분적으로 망가진다.**

### 2-3. 주문 이력 문제

메뉴 15개는 `order_item` 16,817행이 참조한다. FK 제약 때문에 그냥 지울 수 없고, 지우려면
주문 이력을 함께 지워야 한다. **전체 주문의 30%(15,291건)가 영향을 받는다.**

`menu` 에는 `deleted_at` 이 있으므로 soft delete 는 가능하다. 그러나 옵션(`opt_item`)에는
soft delete 컬럼이 없다.

## 3. 대신 권하는 것

PDF 대조는 **단종 후보를 찾는 참고 자료**로 쓰고, 실제 정리는 근거를 나눠서 한다.

### 3-1. 지금 바로 정리해도 안전한 것

「재료 빼기」 중 **깨진 재료로 만들어진 것**들이다. 주문 0건이고 화면에 뜻 모를 문구로 노출된다.

| opt_item | 이름 | 주문 |
|---|---|---|
| 6292 | `(*채소믹스 미포함 빼기` | 0 |
| 6295 | `드레싱 미제공) 빼기` | 0 |
| 6823 | `화이트치즈 (*채소믹스 미포함) 빼기` | 0 |
| 9421 | `참기름 (*채소믹스 미포함 빼기` | 0 |

원본에서 `화이트치즈 (*채소믹스 미포함, 드레싱 미제공)` 같은 한 문장이 쉼표로 쪼개져 재료로
등록된 결과다. 이건 PDF 와 무관하게 데이터 오류다.

### 3-2. 담당자 확인이 필요한 것

메뉴 15개 중 **정말 단종인지** 확인이 필요하다. PDF 미수록과 단종은 다르다.

특히 주문이 많은 것들이다 — `랜치 콥 샐러디`(2,414건), `로스트닭다리살마요 덮밥`(2,214건),
`노릇노릇두부 포케볼`(2,033건), `BELT 시저 샌드위치`(1,971건).

단종이 확정되면 **`menu.deleted_at` 으로 soft delete** 한다. 주문 이력은 보존된다.

### 3-3. 이름 표기 차이일 뿐인 것

PDF 와 DB 의 이름이 달라 "없음"으로 잡혔을 뿐 같은 것일 수 있다.

| DB | PDF 후보 |
|---|---|
| `우삼겹메밀면 누들볼` | `우삼겹메밀 누들볼` (‘면’ 한 글자) |
| `베이컨` | `칩베이컨` (다른 품목일 수도) |
| `잠봉 샌드위치` | `[프로틴]프레시 잠봉 샌드위치` |
| `바질연어 샌드위치` | `[프로틴]바질 레몬연어 샌드위치` |

이름을 맞출지, 별개로 둘지 판단이 필요하다.

### 3-4. 운영 결정 기록 (2026-08-19)

PDF 미수록 여부는 삭제 기준으로 쓰지 않는다. 아래는 담당자와 합의한 처리 기준이며, **코드·DB에는 아직 반영하지 않았다.**

| 대상 | 원하는 처리 | 실제 필요한 방식 | 현재 상태 |
| --- | --- | --- | --- |
| 깨진 「빼기」 옵션 4개 (`6292`, `6295`, `6823`, `9421`) | 즉시 숨김 | 해당 `opt_policy_item.active=0` + 고객 조회·주문 검증에 `opi.active=1` | 반영 대기 |
| 메뉴 15개 | 단종 후보 비노출 | `menu.deleted_at`에 시각 기록하는 soft delete | 반영 대기 |
| 드레싱 4종·토핑 4종 | 일시 비노출 | 해당 `opt_policy_item.active=0` + 동일 조회·주문 검증 조건 | 반영 대기 |
| 생수 330ml | 유지 | 변경 없음 | 결정됨 |
| 정상 「재료 빼기」 | 유지 | PDF가 아니라 메뉴 레시피의 `menu_ing.can_remove=1` 기준 | 결정됨 |

#### `active`의 의미와 적용 범위

- `opt_policy_item`은 `opt_policy`와 `opt_item`을 연결하는 **정책별 옵션 연결** 테이블이다. `active`는 중복 옵션 정리에서 새로 만든 컬럼이 아니라, 최소 2026-08-07 DDL에 이미 존재하던 상태값이다.
- `active=0`은 해당 정책에서 옵션을 신규 노출·선택하지 않는다는 뜻이다. 같은 `opt_item`이 다른 정책에 연결됐다면 그 연결에는 영향을 주지 않는다.
- 깨진 「빼기」 4개는 중복 옵션 42쌍과 다른 데이터 오류다. 주문 0건이며, 원문 문장이 잘못 분리되어 만들어졌다.
- 현재 `UserMenuMapper.selectOptionItems`와 `UserOrderMapper`의 옵션 검증 쿼리는 `opi.active`를 조건으로 쓰지 않는다. 따라서 DB에서 `active`만 0으로 바꾸면 화면과 주문 검증에 효과가 없다.
- 코드 반영 시 고객 옵션 조회와 주문 검증의 정책-옵션 조인에 `AND opi.active = 1`을 추가한다. 이 작업은 별도의 코드 수정 승인과 API·키오스크 회귀 확인이 필요하다.

#### 메뉴 soft delete의 확인·복구

현재 키오스크 메뉴 목록·상세 조회는 `m.deleted_at IS NULL`을 조건으로 사용한다.

1. 대상 메뉴의 `deleted_at`을 현재 시각으로 갱신하면 키오스크 목록과 상세에서 제외된다.
2. `order_item.menu_id`와 주문 이력은 변경하지 않으므로 과거 주문은 보존된다.
3. 반영 후 대상 15개의 `deleted_at` 값, 키오스크 목록·상세 미노출, 과거 주문 상세 조회를 확인한다.
4. 단종 결정을 되돌리면 대상 행의 `deleted_at`을 `NULL`로 갱신해 복구한다.

> 메뉴에는 `active` 컬럼이 없다. 메뉴 비노출은 `sold_out`(일시 품절)이 아니라 `deleted_at` soft delete로 처리한다.

## 4. 그래도 전면 적용한다면

요청대로 교집합만 남기려면 순서와 방식은 이렇다. **위 2절을 읽고도 진행할 때만 쓴다.**

```sql
-- 0) 백업 (필수)
CREATE TABLE backup_20260819_menu_before_pdf_cut AS SELECT * FROM menu;
CREATE TABLE backup_20260819_opt_item_before_pdf_cut AS SELECT * FROM opt_item;
CREATE TABLE backup_20260819_opt_policy_item_before_pdf_cut AS SELECT * FROM opt_policy_item;

-- 1) 메뉴는 지우지 말고 soft delete (주문 이력 보존)
UPDATE menu SET deleted_at = NOW()
WHERE id IN (8065,3523,2820,7851,2114,6275,2534,7160,3105,4450,3388,10789,1568,7958,4185);

-- 2) 옵션은 정책 연결만 끊는다 (주문 이력 보존)
DELETE pi FROM opt_policy_item pi
WHERE pi.opt_item_id IN (247,259,265,273,248,260,266,274,325,283,282,288,
                         6292,3533,9817,1844,1847,6295,2539,1850,3931,2120,9421,1853,6929,6823,379);
```

**`opt_item` 행 자체는 지우지 않는다.** `order_item_option` 43,497행이 참조하므로 삭제하면
주문 이력이 깨진다. 정책 연결만 끊으면 화면에서 사라지면서 이력은 남는다.

> 이 절의 정책 연결 `DELETE` 방식은 현재 운영 결정으로 채택하지 않았다. 주문 이력을 보존하면서
> 일시 비노출하려면 3-4절의 `active=0`과 Mapper 조건 반영을 함께 적용한다.

### 되돌리기

```sql
UPDATE menu m JOIN backup_20260819_menu_before_pdf_cut b ON b.id = m.id
SET m.deleted_at = b.deleted_at;

DELETE FROM opt_policy_item;
INSERT INTO opt_policy_item SELECT * FROM backup_20260819_opt_policy_item_before_pdf_cut;
```
